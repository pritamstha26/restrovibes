# 4.1 Implementation

In this phase, the theoretical design is turned into practice, i.e., a working system. It is the most crucial stage of the project, as it produces the final system and gives confidence to the users that the RestroVibes restaurant appointment booking platform will work efficiently and effectively. The system is implemented only after thorough testing is carried out and it is found to work according to the specification. This chapter presents the tools used to build both the front end and the back end of the system, followed by the implementation details of each functional module.

## 4.1.1 Tools Used

The various tools that have been used in developing both the front-end and backend of the project are discussed in this chapter.

**Front end: HTML, CSS, JavaScript, React, Vite, Tailwind CSS, Bootstrap, Axios, React Router, Leaflet**

**HTML**
All the webpages that are viewed are written in a front-end language called HTML (Hyper Text Markup Language). HTML can be thought of as the skeleton that gives every webpage structure and helps to display all the tags written inside an HTML file.

**CSS**
Cascading Style Sheets (CSS) is the styling language used alongside HTML to control the visual presentation of the application. It governs layout, colors, spacing, and responsiveness, ensuring that all pages of the RestroVibes platform appear clean and consistent across different devices.

**JavaScript**
JavaScript is the programming language of the web that adds interactivity and dynamic behavior to the pages. In RestroVibes it handles form validation, state management, API communication, and real-time updates such as seat availability and appointment status changes.

**React**
React is a JavaScript library for building user interfaces through reusable, component-based architecture. Each screen of RestroVibes, such as the client dashboard, restaurant profile, booking flow, and admin panel, is composed of independent React components that manage their own state, making the interface modular, maintainable, and fast to update.

**Vite**
Vite is a modern build tool and development server used to scaffold and bundle the front end. It provides fast hot module replacement (HMR) so that changes made during development appear instantly in the browser, and it produces an optimized production build for deployment.

**Tailwind CSS**
Tailwind CSS is a utility-first CSS framework used for designing modern and responsive user interfaces. It provides pre-defined utility classes that allow developers to style elements directly in the markup without writing custom CSS, and it is used across RestroVibes to create clean, consistent, and responsive designs efficiently.

**Bootstrap / React-Bootstrap**
Bootstrap is a popular front-end component framework, and React-Bootstrap is its React integration. It provides ready-made, accessible components such as modals, navigation bars, forms, and cards. In RestroVibes, Bootstrap components are used for pricing breakdown modals, booking forms, and the admin dashboard layout.

**Axios**
Axios is a promise-based HTTP client used to communicate between the front end and the backend API. It simplifies sending asynchronous requests and is configured with interceptors that automatically catch expired access tokens, refresh them, and retry the original request without interrupting the user.

**React Router**
React Router Dom is the client-side routing library used to navigate between pages of the single-page application (SPA). It enables seamless transitions between views such as login, signup, dashboard, restaurant profile, and admin panel without reloading the page.

**Leaflet**
Leaflet is an open-source interactive map library, integrated with React through React-Leaflet. It renders restaurants on a map using OpenStreetMap tiles, allowing clients to explore nearby restaurants based on their current GPS location.

**Back end: Node.js, Express, Sequelize, PostgreSQL**

**Node.js**
Node.js is a JavaScript runtime built on Chrome's V8 engine that executes JavaScript on the server. It enables the backend of RestroVibes to be written in a single language, JavaScript, and handles many concurrent connections efficiently, which is well suited to a real-time booking platform.

**Express**
Express is a minimal and flexible web framework for Node.js used to build the RESTful API. It handles routing, middleware (such as authentication and file uploads), and HTTP request/response processing. Every endpoint of the system, such as booking, rating, and location discovery, is defined as an Express route.

**Sequelize**
Sequelize is an Object Relational Mapping (ORM) library for Node.js. It maps database tables to JavaScript models, manages associations between tables, and handles queries, migrations, and seed data. This allows the developers to work with the PostgreSQL database through model classes instead of writing raw SQL.

**PostgreSQL**
PostgreSQL is a powerful open-source relational database management system used for storing and managing the structured data of the platform. It supports advanced SQL features such as ENUM types and JSON, ensures data integrity through constraints and foreign keys, and provides high reliability and scalability, making it suitable for storing users, appointments, services, tables, and ratings.

**MS Office**
MS Office is used for writing and editing the documentation of the RestroVibes restaurant booking platform.

**Draw.io**
Draw.io is used to generate the system analysis and design diagrams of the platform, such as use case diagrams, ER diagrams, and architecture diagrams. Diagrams were created using this tool in order to save time since all components are available with drag-and-drop functions.

## 4.1.2 Implementation Details of Modules

According to the requirements, the RestroVibes system is divided into several main functional modules to ensure clear separation of responsibilities and efficient system management.

**User Module:** This module handles authentication and account management for all users of the platform. Users can register, log in, and recover their password through the forgot/reset password flow. On registration, passwords are hashed using bcrypt and never stored in plaintext. Successful login issues a pair of short-lived access and refresh JSON Web Tokens (JWT), which the front end automatically refreshes through Axios interceptors when they expire. The module also enforces role-based access control, distinguishing between three roles: client, restaurateur, and admin.

**Client Module:** This module handles all customer-related functionalities. Clients can browse restaurants, discover nearby restaurants on an interactive Leaflet map using their GPS location, view detailed restaurant profiles with services and prices, and book tables or request services. Clients can also track the status of their bookings, view their reliability status, view booking history, and rate the restaurants they have visited.

**Restaurateur Module:** This module is responsible for managing restaurants within the RestroVibes system. It allows restaurateurs to configure their store profile and location, manage the services they offer, and set the seat capacity (the number of tables) of their restaurant. The module handles incoming appointment requests, allowing restaurateurs to accept or reject bookings based on availability, table capacity, and their own conditions. Restaurateurs can also mark clients as arrived, complete appointments, and mark no-shows to keep the seating accurate.

**Booking Module:** The Booking (Appointment) Module handles the complete appointment process from request creation to completion. It manages the appointment status lifecycle, including pending, accepted, rejected, cancelled, in_progress, completed, and no_show. The module enforces business rules such as minimum one-hour gaps between bookings at the same restaurant, service-hours validation, table capacity enforcement, and detection of competing bookings for the same time slot. It also integrates background workers: the auto-accept worker automatically accepts solo pending bookings after a grace period, and the overstay worker automatically completes expired appointments or marks stale bookings as no-shows.

**Reliability Scoring Module:** This module computes a penalty score (0 to 1) for every client based on their booking behavior, weighting no-shows, late arrivals, late cancellations, and overstays. Each client is classified as reliable, at-risk, or flagged, and this status is shown to restaurateurs through a colored indicator beside the client's name. The score is recalculated automatically after every booking status change when new history entries are created.

**Admin Module:** The Admin Module oversees the overall system operation. It provides a dashboard for managing all users, restaurants, bookings, services, and tables. It allows administrators to review client lists with their reliability data, monitor restaurant performance, and maintain control over platform activities to ensure the smooth functioning of the system.

## 4.1.3 Key Algorithms Implemented

This section describes the core algorithms implemented in the RestroVibes system to automate booking decisions, enforce client reliability, discover nearby restaurants, and resolve slot conflicts fairly.

### 4.1.3.1 Client Reliability Penalty Scoring

The system quantifies each client's reliability as a single penalty score in the range [0, 1] computed from their booking history. All signals (no-shows, late arrivals, late cancellations, overstays) are aggregated into a raw penalty, then reduced by a decay term that rewards completed bookings:

```
rawPenalty    = (n_ns × w_ns + n_la × w_la + n_lc × w_lc + n_os × w_os) / n_total
completionRatio = n_completed / n_total
decay          = min(completionRatio × 0.15, rawPenalty × 0.3)
penaltyScore   = max(0, rawPenalty - decay)
```

where n_ns, n_la, n_lc, and n_os are the counts of no-shows, late arrivals, late cancellations, and overstays, and w_ns = 0.7, w_la = 0.4, w_lc = 0.3, w_os = 0.15. The weights reflect the economic impact of each behaviour: a no-show is weighted highest (0.7) because the restaurant loses the entire slot with no opportunity to rebook, while an overstay is weighted lowest (0.15). The decay cap of 30% of the raw penalty ensures good behaviour improves a score but can never fully erase a poor record. The engine recomputes and caches the score on the user record after every booking status change (`recalculateUserPenalty`), so reads during appointment listing remain O(1) per user.

The resulting score is mapped to a verdict through configurable thresholds:

| Penalty Score | Status | Visual Indicator |
|---|---|---|
| 0 – 0.15 | reliable | Green dot |
| 0.15 – 0.4 | at_risk | Yellow dot |
| > 0.4 | flagged | Red dot |

### 4.1.3.2 Late Arrival Detection

When a restaurateur confirms a client's arrival, the system compares the signed difference between actual arrival time and scheduled time:

```
Δt = (t_arrival − t_scheduled) / (1000 × 60)
```

If Δt > 15 minutes, the appointment is flagged `is_late`, a "late_arrival" entry is appended to booking history, and the reliability score is recalculated. If Δt ≤ 0, the client is on time and no penalty is applied. The 15-minute threshold acts as a single tunable constant separating acceptable and penalized lateness.

### 4.1.3.3 Haversine Distance for GPS Discovery

Nearby-restaurant discovery computes the great-circle distance between the client's coordinates (lat1, lng1) and each restaurant's coordinates (lat2, lng2):

```
a  = sin²(Δlat/2) + cos(lat1) · cos(lat2) · sin²(Δlng/2)
c  = 2 · atan2(√a, √(1 − a))
d  = R · c                    (R = 6,371 km, Earth's mean radius)
```

Because all coordinates are passed through trigonometric functions once per comparison, the operation is evaluated in constant time per restaurant, and travel time is estimated as t = d / v with a constant assumed average speed of v = 30 km/h. External routing APIs (Google Maps, Mapbox, OpenRouteService) were evaluated but rejected due to paid billing, inaccurate demo tokens, and access restrictions; the straight-line distance is sufficient for the "nearby" ranking use case.

### 4.1.3.4 Weighted Lottery for Slot Conflicts

When multiple clients compete for the same time slot, the system resolves the conflict by weighted random selection. Each entry i is first assigned a base weight drawn from two normalized signals — loyalty score l ∈ [0,1] and penalty score p ∈ [0,1]:

```
W_i  = BASE + (l_i × β) − (p_i × γ)
```

with BASE = 100, β = 30, γ = 200. The loyalty score is the weighted combination of restaurant-specific, platform-wide, and account-age sub-scores; and the penalty score reduces weight, making unreliable clients less likely to win. The reliability score is the strongest factor at γ = 200, so flagged or at-risk clients are strongly disadvantaged in contested slots.

The base weight is then boosted by an exponential **time-decay (aging) factor** so that entries which have waited longer gain increasing strength over time, preventing stale entries from starving:

```
agingFactor(t) = 1 − 0.5^(t / h)
W_eff,i = W_i × (1 + min(agingFactor(t_i) × B_max, B_max))
```

where t_i is the time since entry i entered the pool (in hours), h = 6 hours is the half-life, and B_max = 3 is the maximum aging boost. After one half-life (6 hours) an entry has gained half of the possible boost, and it saturates at a maximum effective weight of 4 × W_i. Because the boost is proportional to the base weight, reliable and loyal clients still win more often, while the growing weight of older entries guarantees fairness for early joiners. Winner selection uses weighted random sampling proportional to W_eff, after which the winner's appointment is `accepted` and the losers are `cancelled`. The lottery is scheduled by `lotteryScheduler.js` and runs alongside the manual accept/reject flow, so a restaurateur can still decide on a slot before the lottery closes it.

### 4.1.3.5 Competing Bookings Detection

For every pending appointment, the system aggregates competing demand using hashed slot keys:

```
key_i          = hash(restaurantId, date_truncated_to_hour)
competingCount = |{ j : key_j = key_i, status = "pending" }|
```

The count is computed with a single GROUP BY over pending appointments and displayed as an "N competing" badge when N > 1, giving restaurateurs an at-a-glance view of contested time slots.

### 4.1.3.6 Dynamic Pricing

The service price presented to a client is the sum of a base price and three additive surcharges:

```
total = basePrice + Δd + Δz + Δh
```

where Δd is the distance fee, Δz is the zone surcharge, and Δh is the peak-hour surcharge. The zone is derived from distance: Local (0–3 km, Δz = 0), Mid-range (3–8 km, Δz = 6), Long-range (>8 km, Δz = 12); Δd = 1.5 × distance; and Δh = 8 when the slot falls in a peak hour, 0 otherwise. A breakdown modal in the client UI presents each component alongside a demand indicator so every price is fully transparent.

### 4.1.3.7 Automated Appointment Lifecycle

The booking lifecycle is automated by two independent background workers that poll at fixed intervals:

| Worker | Interval | Grace Period (τ) | Purpose |
|---|---|---|---|
| Auto-Accept Worker | 2 minutes | 20 minutes | Accepts pending bookings with no competition |
| Overstay Worker | 60 seconds | 10 minutes | Enforces time limits and releases seats |

**Auto-Accept logic:** For every pending appointment with age > τ, appointments are grouped by slot. A slot holding exactly one pending booking is auto-accepted; a slot holding two or more is left for manual review or the lottery.

**Overstay logic:** For every appointment past its end time plus τ, an `in_progress` appointment is marked `completed` (recorded as "overstayed"), while a `pending` or `accepted` appointment is marked `no_show`; the client's reliability score is recalculated after each transition. This guarantees that abandoned bookings release their reserved seats automatically without manual intervention.
