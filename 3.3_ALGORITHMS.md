# 3.3 Algorithm Design and Implementation

This chapter presents the underlying algorithms of the RestroVibes system. Each algorithm is described with its mathematical formulation, the meaning of every symbol, its decision thresholds, and the flow it follows during execution. Together, these algorithms automate booking decisions, enforce client reliability, discover nearby restaurants, resolve slot conflicts fairly, and keep appointment lifecycles accurate with minimal manual intervention.

## 3.3.1 Client Reliability Scoring

### 3.3.1.1 Penalty Score Computation

The system quantifies each client's reliability as a single penalty score in the range [0, 1], computed from their booking history. All signals — no-shows, late arrivals, late cancellations, and overstays — are aggregated into a raw penalty which is then reduced by a decay term that rewards completed bookings:

```
rawPenalty      = (n_ns × 0.7 + n_la × 0.4 + n_lc × 0.3 + n_os × 0.15) / n_total
completionRatio = n_completed / n_total
decay           = min(completionRatio × 0.15, rawPenalty × 0.3)
penaltyScore    = max(0, rawPenalty − decay)
```

where:

- n_ns, n_la, n_lc, n_os = counts of no-shows, late arrivals, late cancellations, and overstays
- n_completed = number of completed bookings
- n_total = total number of bookings

**Weight justification.** Each behaviour is weighted by its economic impact on the restaurant:

| Behaviour | Weight | Rationale |
|---|---|---|
| No-show | 0.7 | Highest impact — the restaurant loses the entire slot with no chance to rebook |
| Late arrival | 0.4 | Disrupts the schedule, but the client still arrives |
| Late cancellation | 0.3 | The restaurant has some time to fill the slot |
| Overstay | 0.15 | Minor inconvenience, normally resolved by the overstay worker |

**Decay mechanism.** Completed bookings provide a capped decay that rewards good behaviour but never fully erases a poor record. The decay is capped at 15% of the completion ratio and 30% of the raw penalty, preventing complete forgiveness.

### 3.3.1.2 Verdict Classification

The continuous penalty score is mapped to a discrete reliability status using configurable thresholds:

| Penalty Score | Status | Visual Indicator |
|---|---|---|
| 0 – 0.15 | reliable | Green dot |
| 0.15 – 0.4 | at_risk | Yellow dot |
| > 0.4 | flagged | Red dot |

The status is cached on the user record after every recalculation (`recalculateUserPenalty`), so that reading the status during appointment listing remains an O(1) operation per user.

### 3.3.1.3 Flow

```
START
  │
  ▼
Booking status change (completed / no_show / late_cancelled / late_arrival / overstayed)
  │
  ▼
BookingHistory entry created
  │
  ▼
Count statuses for the user (GROUP BY status)
  │
  ▼
rawPenalty = (ns×0.7 + la×0.4 + lc×0.3 + os×0.15) / total
decay      = min(completionRatio × 0.15, rawPenalty × 0.3)
penalty    = max(0, rawPenalty − decay)
  │
  ▼
Classify: ≤0.15 → reliable | 0.15–0.4 → at_risk | >0.4 → flagged
  │
  ▼
Cache on user record (single UPDATE)
  │
  ▼
Displayed to restaurateur as colored dot → END
```

## 3.3.2 Late Arrival Detection

When a restaurateur marks a client as arrived, the system computes the signed time difference between the actual arrival and the scheduled time:

```
Δt = (t_arrival − t_scheduled) / (1000 × 60)     (in minutes)
```

The verdict is produced by a simple threshold comparison:

```
if Δt > 15:
    appointment.is_late = true
    create BookingHistory entry with status "late_arrival"
    recalculate client penalty
else:
    on time — no penalty applied
```

The 15-minute constant is a single tunable parameter separating acceptable and penalized lateness.

```
START → restaurateur confirms arrival → compute Δt
   ┌────────────────┴────────────────┐
   ▼                                 ▼
Δt > 15                          Δt ≤ 15
   │                                 │
   ▼                                 ▼
flag is_late                     no penalty
create history                   → END
recalculate penalty
   │
   ▼
END
```

## 3.3.3 Haversine Distance for GPS Discovery

### 3.3.3.1 Distance Formula

Nearby-restaurant discovery computes the great-circle distance between the client's coordinates (lat₁, lng₁) and each restaurant's coordinates (lat₂, lng₂):

```
a = sin²(Δlat/2) + cos(lat₁) · cos(lat₂) · sin²(Δlng/2)
c = 2 · atan2(√a, √(1 − a))
d = R · c
```

where R = 6,371 km is the Earth's mean radius, Δlat = lat₂ − lat₁, and Δlng = lng₂ − lng₁.

### 3.3.3.2 Travel Time Estimation

The estimated travel time for each restaurant is computed assuming a constant average speed:

```
t = d / v        (v = 30 km/h)
```

### 3.3.3.3 Design Choice

External routing APIs (Google Maps, Mapbox, OpenRouteService) were evaluated and rejected: Google Maps requires paid billing, Mapbox demo tokens produce inaccurate distances, and OpenRouteService returns 403 for this use case. The straight-line (Haversine) distance is therefore sufficient for the "nearby" ranking requirement, and it runs in constant time per restaurant.

### 3.3.3.4 Flow

```
START → read client GPS coordinates
  │
  ▼
for each restaurant: d_i = Haversine(client, restaurant_i)
  │
  ▼
filter restaurants within radius / rank by d_i
  │
  ▼
t_i = d_i / 30 km/h
  │
  ▼
render on Leaflet map, sorted by distance + occupancy → END
```

## 3.3.4 Weighted Lottery for Slot Conflicts

### 3.3.4.1 Base Weight

When multiple clients compete for the same time slot, the system resolves the conflict by weighted random selection. Each entry i first receives a base weight combining three normalized signals, each in [0, 1]:

```
W_i = BASE + (φ_i × α) + (l_i × β) − (p_i × γ)
```

with BASE = 100, α = 50, β = 30, and γ = 200, where:

- φ_i = flexibility score — derived solely from the declared flexibility window (≤30 min → 0.4, 31–60 min → 0.7, >60 min → 1.0)
- l_i = loyalty score — weighted combination of restaurant-specific (×0.5), platform-wide (×0.3), and account-age (×0.2) sub-scores
- p_i = penalty score — reduces weight so that unreliable clients are less likely to win

The result is clamped to a minimum of W_i = 1, so a floor of 1 keeps every entry eligible for the draw.

### 3.3.4.2 Time-Decay Aging Factor

The base weight is boosted by an exponential aging factor so that entries which have waited longer gain increasing strength, preventing early entries from starving:

```
aging(t) = 1 − 0.5^(t / h)
W_eff,i  = W_i × (1 + min(aging(t_i) × B_max, B_max))
```

where t_i = (drawTime − entered_at,i) / 3,600,000 is the age of entry i in hours measured at the moment of the draw, h = 6 hours is the half-life, and B_max = 3 is the maximum aging boost. At half-life an entry has gained half of the possible boost; growth is exponential and asymptotically capped, so the effective weight approaches (but never reaches) 4 × W_i.

| Waiting time | aging(t) | agingBoost | multiplier |
|---|---|---|---|
| 0 h | 0.000 | 1.00 | × 1.00 |
| 3 h | 0.293 | 1.88 | × 1.88 |
| 6 h | 0.500 | 2.50 | × 2.50 |
| 12 h | 0.750 | 3.25 | × 3.25 |
| 24 h | 0.938 | 3.81 | × 3.81 |
| → ∞ | 1.000 | 4.00 | × 4.00 (asymptote) |

The boost is proportional to the base weight, so reliable and loyal clients still win more often, while older entries gain a growing chance — time decay rewards patience without ever overriding client quality. Because the boost is a multiplier on W_i, the earlier an entry joins the pool the larger its boost (up to the ×4 asymptote), but the advantage only tilts contests between otherwise similar entries.

### 3.3.4.3 Resolution Timing of the Boost

The boost is frozen at the instant the lottery is drawn, so when the draw fires determines how much aging accumulates:

- Slots contested on **today or tomorrow** are drawn ~1 minute after the second entrant joins (the lottery scheduler polls every 60 seconds). Decay therefore equals the head-start of the earlier entrant — negligible when entrants arrive back-to-back, significant when one sat alone for hours.
- Slots dated further out are **not drawn until their booking date enters the today/tomorrow window**, so entries can accumulate days of aging, generally reaching the ×4 asymptote.
- A restaurateur may also **resolve manually** at any time; aging keeps growing while the slot is under review.

The auto-accept worker (2-minute poll, 20-minute grace) is a separate mechanism that only promotes slots holding a single pending appointment; it does not run the lottery.

### 3.3.4.4 Winner Selection

Winner selection samples entries proportional to their effective weights:

```
total = Σ W_eff,i
threshold = random × total        (random ∈ [0, 1))
for each entry: threshold −= W_eff,i; if ≤ 0 → winner
```

The winner's appointment is set to `accepted` and the losers' appointments to `cancelled`.

### 3.3.4.5 Flow

```
START → collect pending entries for the contested slot
  │
  ▼
W = 100 + (flex × 50) + (loyalty × 30) − (penalty × 200)   (min 1)
  │
  ▼
t = (now − entered_at) / 3,600,000   (hours at draw time)
aging = 1 − 0.5^(t / 6)
W_eff = W × (1 + min(aging × 3, 3))
  │
  ▼
total = Σ W_eff
  │
  ▼
threshold = random × total  →  weighted random walk
  │
  ├──────────────────────► Winner  → status "won",  appointment accepted
  │
  └──────────────────────► Losers  → status "lost", appointments cancelled
  │
  ▼
END
```

## 3.3.5 Competing Bookings Detection

### 3.3.5.1 Slot Aggregation

For every pending appointment, the system counts competing demand using hashed slot keys:

```
key_i          = hash(restaurant_id, date_truncated_to_hour)
competingCount = |{ j : key_j = key_i, status = "pending" }|
```

The count is computed with a single GROUP BY over pending appointments and rendered as an "N competing" badge when N > 1, so restaurateurs can spot contested time slots at a glance.

### 3.3.5.2 Flow

```
START → fetch appointments for the restaurateur
  │
  ▼
group pending bookings by (restaurant, hour)
  │
  ▼
competingCount = |group(i)| − 1
  │
  ▼
if competingCount > 1 → show "N competing" badge → END
```

## 3.3.6 Dynamic Pricing

### 3.3.6.1 Price Composition

The price presented to a client is the sum of a base price and three additive surcharges:

```
total = basePrice + Δd + Δz + Δh
```

where:

- Δd = distance fee = 1.5 × distance (flat rate per kilometre)
- Δz = zone surcharge, derived from distance zones: Local (0–3 km, Δz = 0), Mid-range (3–8 km, Δz = 6), Long-range (>8 km, Δz = 12)
- Δh = peak-hour surcharge = 8 during peak hours, otherwise 0

A pricing breakdown modal in the client interface presents each component alongside a demand indicator, making every price change transparent.

### 3.3.6.2 Flow

```
START → selected service and slot
  │
  ▼
compute distance d between client and restaurant
  │
  ▼
zone = Local | Mid-range | Long-range   (from d)
Δz   = 0 | 6 | 12
Δd   = 1.5 × d
Δh   = peak hour ? 8 : 0
  │
  ▼
total = basePrice + Δd + Δz + Δh
  │
  ▼
render breakdown modal (base → surcharges → total) → END
```

## 3.3.7 Automated Appointment Lifecycle

### 3.3.7.1 Background Workers

The booking lifecycle is automated by two independent background workers that poll at fixed intervals:

| Worker | Interval | Grace Period (τ) | Purpose |
|---|---|---|---|
| Auto-Accept Worker | 2 minutes | 20 minutes | Accepts pending bookings with no competition |
| Overstay Worker | 60 seconds | 10 minutes | Enforces time limits and releases seats |

### 3.3.7.2 Auto-Accept Rule

For every pending appointment older than τ, appointments are grouped by slot. A slot holding exactly one pending booking is accepted automatically; a slot holding two or more is left for manual review or the lottery:

```
if age(pending) > 20 min:
    group by slot
    if |group| == 1 → status = accepted
    if |group| ≥ 2 → leave for manual review / lottery
```

### 3.3.7.3 Overstay Rule

For every appointment past its end time plus τ:

```
if status == "in_progress"     → status = completed, history = "overstayed"
if status == "pending"|"accepted" → status = no_show, history = "no_show"
recalculate client penalty after each transition
```

This guarantees that abandoned bookings release their reserved seats automatically without manual intervention.

### 3.3.7.4 Flow

```
┌─────────────────────────────┐   ┌──────────────────────────────┐
│  AUTO-ACCEPT WORKER        │   │  OVERSTAY WORKER            │
│  (every 2 minutes)         │   │  (every 60 seconds)         │
└──────────────┬──────────────┘   └──────────────┬───────────────┘
               ▼                                 ▼
  fetch pending older than 20 min    fetch appointments past
               │                    end time + 10 min
               ▼                                 │
  group by slot (restaurant + hour)              │
  ┌─────────────┴────────────┐                    │
  ▼                           ▼                   │
 1 pending                2+ pending              │
 auto-accept               manual / lottery       │
 status=accepted                                  │
               └────────────────┬─────────────────┘
                                ▼
              1) in_progress       2) pending/accepted
                 │                      │
                 ▼                      ▼
         completed(overstayed)   no_show(history)
                 │                      │
                 └──────────┬───────────┘
                            ▼
              recalculate client penalty → END
```

## 3.3.8 End-to-End Booking Decision Flow

The algorithms above are combined in the complete booking flow. The system first validates the request, then decides whether to route it directly or through the lottery, and finally applies the reliability and lifecycle machinery:

```
START → client selects restaurant, service, date, time slot
  │
  ▼
validate: service hours, min 1-hour gap, seat capacity
  │
  ├─────────────────────────── Failed → reject booking
  ▼
slot already contested? ── No ──► direct pending booking
  │ Yes                             │
  ▼                                 ▼
enter lottery pool               auto-accept worker
  │ (time-decay aging)           (accepts solo bookings)
  ▼
lottery resolution →                 │
  Winner: accepted                   │
  Losers: cancelled                  │
  │                                  │
  └──────────────────────────────────┘
                 │
                 ▼
restaurateur confirms arrival?  ──No──► overstay/no_show
                 │ Yes                   │
                 ▼                       ▼
late detection (Δt>15)            penalty recalculated
                 │
                 ▼
status in_progress → completed → rating → history
                 │
                 ▼
               END
```
